**4. P1：自动链接追踪缺少目标地址边界，可以访问本机或内网服务。**

位置：[chains.py:45](/Users/langjiahui/Documents/AIpro/mail+AI/app/security/chains.py:45)、[pipeline.py:253](/Users/langjiahui/Documents/AIpro/mail+AI/app/pipeline.py:253)。

邮件里的 IP 直连和短链接会自动进入网络追踪，但追踪前及重定向时没有限制回环、私网、链路本地等地址，也没有对每跳解析结果做验证。这构成由邮件内容触发的服务端请求伪造风险：收件人不需要点击链接，后台就可能访问本机或企业内网端点。

**5. P2：链接追踪会记录错误的最终地址，跳数限制也没有按预期生效。**

位置：[chains.py:55](/Users/langjiahui/Documents/AIpro/mail+AI/app/security/chains.py:55)、[chains.py:84](/Users/langjiahui/Documents/AIpro/mail+AI/app/security/chains.py:84)。

`urlopen` 默认处理重定向，而当前代码又试图在外层读取 3xx 和 Location 手工追踪。收到的可能已是最终 200 响应，却仍被标记为起始 URL，随后落地域名检测也针对起始地址执行。[Python 官方 urllib 文档](https://docs.python.org/3/library/urllib.request.html#httpredirecthandler-objects)说明了默认重定向处理行为。

本地复现 `/start → /internal → 200`，即使 `max_hops=1`，服务仍收到两次请求；报告只有一个 200 节点，最终地址仍为 `/start`。因此报告中的跳转链和最终落地信息不可靠，最终域名黑名单或仿冒域检测可能漏报。

建议禁用隐式重定向，逐跳执行、校验和记录；使用总时限与真实请求次数限制，测试跨域跳转、循环、不同重定向状态码及失败响应。
