# 代码签名与升级身份

MailAI 官方 macOS 发布必须使用固定身份签名；缺少凭据时停止构建。Windows 签名仍为可选，本地 macOS 预览可不签名。不要把私钥、P12 或密码提交到 Git。

## macOS 固定自签名（无 Apple 开发者账号）

自 v2.8.8 起，未配置 Developer ID 时使用固定自签名证书。证书公钥保存在 `scripts/signing/mailai-self-signed.pem`，应用身份同时绑定该证书指纹和 `com.langjiahui.mailai`。指纹用于身份匹配，签名摘要仍由 codesign 生成；不可改成仅匹配应用名称，也不可每次生成新证书。

一次性运行 `scripts/create_macos_signing_identity.py <仓库外的新目录>` 创建身份。目录与私密文件使用 0700/0600 权限，已存在目录会拒绝覆盖。将 P12 的 Base64 和密码分别通过标准输入设置为 GitHub 加密 Secrets：`MACOS_SELF_SIGN_CERTIFICATE`、`MACOS_SELF_SIGN_PASSWORD`。仅复制公共 `certificate.pem` 到上述公钥路径。私钥与密码必须保存在安全备份中；丢失或更换意味着用户需要重新授权。

CI 在独立临时钥匙串导入身份，仅允许 codesign 使用私钥，打包结束删除临时钥匙串。`scripts/macos_signing.py` 校验产物证书与应用身份，缺少身份、指纹不符或签名失败均中止。自签名没有 Apple Team ID，因此不启用会阻止 Python 扩展加载的 hardened runtime library validation；Developer ID 路径继续使用 hardened runtime。自签名的 PKG/DMG 不冒充 Apple 签名或公证。

`verify_macos_signing_upgrade.py` 在独立临时钥匙串创建合成凭据，禁止所有授权 UI。它在同一路径依次运行不同构建：固定证书读取成功；临时签名和不同应用标识被拒绝；恢复固定身份后读取成功。测试不访问用户登录钥匙串条目。正式应用签名后还需通过隔离启动与原生钥匙串查询检查。

从旧版临时签名首次迁移仍可能需要用户选择一次“始终允许”，现有条目的授权由系统处理，不自动修改旧 ACL。后续同身份版本可延续授权，但钥匙串锁定、用户撤销权限、证书更换等情况仍可能需要验证。此方案不提供 Touch ID，也不能消除 Gatekeeper 安装来源提示。

## macOS（Developer ID）

需要 Apple Developer Program 的两种证书：

| 用途 | 证书类型 |
| --- | --- |
| 给 `MailAI.app` 签名（codesign） | Developer ID Application |
| 给 `.pkg` 安装器签名（productsign） | Developer ID Installer |

配置步骤：

1. 在 Keychain Access 中把两张证书导出为一个 `.p12`（设置导出密码）。
2. `base64 -i cert.p12 | pbcopy`，在仓库 **Settings → Secrets and variables →
   Actions → Secrets** 新建：
   - `MACOS_CERTIFICATE`：上一步的 base64 文本
   - `MACOS_CERTIFICATE_PASSWORD`：p12 导出密码
   - `MACOS_KEYCHAIN_PASSWORD`（可选）：CI 临时钥匙串密码，缺省自动生成
3. 身份名称缺省从证书自动识别；如需指定，在 **Variables** 中设置
   `MACOS_SIGN_IDENTITY` / `MACOS_INSTALLER_IDENTITY`
   （形如 `Developer ID Application: Your Name (TEAMID)`）。

流水线把证书导入一次性钥匙串 `mailai-signing.keychain-db`，随后
`scripts/build_macos.command` 检测到 `MAILAI_SIGN_IDENTITY` 后用
`codesign --options runtime --timestamp --deep` 给应用签名并立即
`--verify --deep --strict` 校验；检测到 `MAILAI_INSTALLER_IDENTITY` 时
用 `productsign` 给 pkg 签名并 `pkgutil --check-signature` 校验。

### Apple 公证

流水线已接入公证和票据附加。需要先配置上述两种 Developer ID 签名证书，再添加三个仓库 Secret：

- `MACOS_NOTARY_KEY_BASE64`：App Store Connect **团队 API Key** 的 `.p8` 文件经 Base64 编码后的内容。
- `MACOS_NOTARY_KEY_ID`：该 Key 的 ID。
- `MACOS_NOTARY_ISSUER`：团队的 Issuer ID。

构建依次为应用、PKG 和 DMG 提交公证，只有 Apple 返回 `Accepted` 且票据附加、校验成功才继续。最终校验和在签名、公证之后生成。未提供公证配置时保持原有构建方式；配置不完整、审核拒绝或超时会停止构建，不会把它当成公证成功。

本地构建也可使用已保存的钥匙串凭据：设置 `MAILAI_NOTARY_PROFILE` 为 `notarytool store-credentials` 保存的名称，同时提供 `MAILAI_SIGN_IDENTITY` 和 `MAILAI_INSTALLER_IDENTITY`。

此流程已通过模拟成功、审核拒绝和密钥清理测试；需要提供真实证书和凭据后，才能完成 Apple 服务端验收。接入流程本身不会让已经发布的旧安装包获得签名或公证。

## Windows（Authenticode）

需要一张代码签名证书（OV/EV 均可，PFX 格式）：

1. 把 `.pfx` 转 base64，在仓库 Secrets 新建：
   - `WINDOWS_CERTIFICATE`：base64 文本
   - `WINDOWS_CERTIFICATE_PASSWORD`：PFX 密码
2. 流水线在安装器构建完成后用 Windows SDK 自带的 `signtool` 签名
   （SHA-256 + DigiCert 时间戳），并 `signtool verify /pa` 校验。

未配置这两个 secret 时，签名步骤整体跳过，发布不受影响。

## Linux

AppImage 暂无签名（AppImage 生态通常以校验和验证完整性）。
每个产物都附带 `.sha256` 文件，`latest.json` 更新清单中也记录了各平台
安装包的 SHA-256，客户端升级前会校验。
