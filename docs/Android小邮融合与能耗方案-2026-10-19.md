# Android 小邮融合与能耗方案

日期：2026-10-19。状态：设计记录；第一阶段已进入 Android 1.3.0 开发，尚未正式发布。当前实现范围与验收状态见 mobile/android/README.md 和 RELEASE.md，以下计划不代表全部完成。

依据：Android 1.2.0 的独立邮件客户端、现有阅读／写信／检索路径，以及桌面小邮的形象和养成。以当前源码为准：Android 尚无模型调用、待办、养成或跨设备小邮同步。本方案不将这些写成已有功能。

## 产品定位

移动小邮帮助用户缩短当前任务：看懂邮件、找到邮件、写好回复。外观轻、操作短、计算按需，三者一起成立。用户不需要先进入聊天页，再解释自己正在看哪封邮件。

沿用原有嫩芽与信封挎包形象，不重新设计成星芒、魔法棒或机器人。小尺寸只显示辨识度高的主体，装扮细节留到个人页的大预览。邮件内容仍拥有主要空间。

## 入口与页面连接

| 场景 | 入口与默认呈现 | 优先动作 | 返回后的连续性 |
| --- | --- | --- | --- |
| 收件箱 | 现有工具栏放一个小邮头像入口，实际触控至少 48 dp；不新增一行、不增加悬浮球 | 找邮件；继续上次未完成的操作 | 保留账号、查询与列表位置 |
| 阅读邮件 | 同一工具栏位置唤起小邮，底部现有回复／回复全部／转发仍保持 | 提炼要点、起草回复、翻译 | 原邮件阅读位置不变；结果留在该邮件下 |
| 写信 | 现有编辑工具条放文字操作“润色”，不再增加独立底栏 | 润色选中文字；无选中时润色正文 | 预览后才采用，可撤回到采用前版本 |
| 邮箱与设置 | 小邮入口可进入个人页与服务设置 | 形象、近期结果、模型服务 | 不要求先完成养成或模型配置才能收发邮件 |

工具栏宽度不足时保留“返回／页面标题、小邮、更多”，刷新、星标等移入更多菜单，已有下拉刷新或明确菜单入口仍可用。使用实际 320 dp、200% 字号验证，不靠压缩按钮热区容纳更多图标。每个页面只保留一处主要小邮入口。

长按、手势可以作为后续加速方式，但不作为唯一入口。键盘弹出时，编辑区与原有工具优先，不弹出角色挡住输入。

模型配置统一放在“账号与设置 → 小邮与模型服务”，不在小邮窗口常驻设置按钮。首次未配置时提供“前往设置”，返回原任务与阅读位置。

## 默认半屏，任务大了再展开

点击后出现底部面板，先露出当前范围和三项以内操作。阅读场景范围写“这封邮件”，点击可确认来源邮件与账号；收件箱场景写当前邮箱，不能默认跨账号。

示例流程：阅读邮件 → 点小邮 → “提炼要点” → 显示简短要点 → 可返回原文或起草回复。摘要初次只给少量要点，不默认展开长篇聊天记录。用户追问或输入时面板可扩展，系统返回先关闭键盘，再返回面板／邮件；关闭后不丢阅读位置。

面板高度随内容与可用空间调整，不硬锁屏幕比例；大字号、横屏或键盘下允许全高显示和滚动。背景邮件不可误触，焦点留在面板，关闭后回到唤起控件。短位移过渡与系统减少动态效果设置兼容。

结果旁使用直接文字动作：“查看原文”“预览回复”“使用这份文字”。不堆一排难懂的图标。摘要和翻译可选中复制；不使用逐字打字机动画制造等待。

## 第一阶段范围

1. **提炼当前邮件**：只在主动点击后请求。摘要保留来源、待办事项和日期原文，推断与原文分开；缺失信息不补造。
2. **起草回复**：根据当前邮件和用户补充生成可编辑预览；采用后进入现有草稿路径，收件身份、附件、发送确认沿用既有机制。
3. **润色正文**：优先处理选中文字；整篇替换需预览。生成期间继续编辑，采用时发现版本不同则先对照，不覆盖新输入。

自然语言找邮件作为第二阶段：先让模型解释检索条件，再调用现有确定性邮件搜索，列表展示真实结果及实际范围；不让模型凭空给出“找到的邮件”。检索本身可继续使用已有关键词搜索，不依赖模型。

提醒／待办、附件解读、语音和批量简报后置。它们分别需要真实的本地存储与提醒闭环、附件格式支持、系统权限和资源控制，不能先挂空入口。

## 请求、失败与数据保护

- 首次使用说明服务商、发送范围与配置入口；手机直接调用用户配置的模型服务，不依赖电脑开机。邮箱密码绝不发送给模型。没有配置时保留基础邮件功能。
- 默认只送当前操作所需的邮件正文／选中文本，附件、其他邮件与账号不自动加入。邮件内的指令只作为被分析内容，不能触发收发或修改设置。
- 同一时刻仅运行一个前台小邮任务，重复点击复用正在执行的请求。任务绑定账号、邮件键或草稿 ID、内容版本及请求 ID；换邮件、换账号后的迟到结果不能污染新页面。
- 成功结果按账号、内容指纹、任务类型、模型及提示版本缓存，重复打开不重新请求。结果来自旧内容时标注可更新，不静默展示成最新分析。
- 生成内容先作为候选保存，不直接写进草稿。采用时通过草稿存储事务保存，保留可撤回版本；保存失败不显示“已采用”。实际发信仍需原有用户确认。
- 面板马上响应点击，显示“正在整理／停止”；按服务实际输出更新，不编造进度百分比。失败明确显示“没有改动原邮件／草稿”及重试。取消保留可用的部分文字并标记未完成，不当成完整结果。
- 普通旋转和短暂系统对话框不启动第二次请求；真正退后台或锁屏时，保存已接收候选并取消小邮网络请求。恢复后可继续查看，是否重新生成由用户决定，不自动续费请求。取消不等于服务商端必然停止计算或计费，不能作此承诺。

## 能耗作为第一层设计约束

“轻”首先体现在不开着也工作、不用时不持续绘制、不因小功能增加后台唤醒。以下为实现要求，不是已实测的耗电结论。

| 状态 | 小邮行为 | 明确禁止 |
| --- | --- | --- |
| 未使用小邮／入口可见 | 静态小头像，只有普通 UI 事件响应 | 呼吸循环、持续眨眼、粒子、常驻定时器、模型预连接 |
| 主动打开面板 | 按需加载面板和该邮件的本地结果 | 自动扫描整箱、载入全部聊天、自动下载附件 |
| 主动请求模型 | 单请求、受限上下文与输出；流式文字合并更新 | 一 token 一次整页重组、额外打字机动画、并行多模型比较 |
| 请求结束／取消 | 关闭响应体及连接资源、保存候选、停止工作动效 | 结束后残留加载循环、无上限重试、后台继续拉取 |
| 锁屏／真正退后台 | 小邮停止绘制与网络；必要状态落盘 | 常驻服务、悬浮窗服务、自持 WakeLock、精确闹钟保活 |
| 省电／温控限制 | 静态显示，关闭非必要短动作，保留主动文字操作 | 为省动画电量阻止查看邮件，或擅自延长用户设置的收信间隔 |

具体实现约束：

- 沿用 Compose 原生 UI；复用矢量形象，不为一个头像引入额外 WebView、视频、GIF 播放器或大型动画运行时。首期不下载／常驻端侧大模型。
- 动作只发生于用户唤起或任务真实完成，短暂播放一次后静止。省电模式和系统减少动态效果下不播放角色动作。失败、停止不播放完成表情。
- 流式更新合并为适度批次，优先局部文字更新；预设最多每秒约 10 次，最终以真机响应与帧耗时决定。输出已到达就呈现，不为动画延长等待。
- 上下文和输出设上限，长邮件先让用户选择范围或缩小任务。相同请求去重、结果复用；失败由用户重试，第一阶段不做后台自动重试。
- 检索走现有邮件能力，本地联系人补全、模板、签名及文字复制继续本地完成。新邮件通知不触发 AI，不启动全箱自动摘要；无额外后台 AI Worker 或心跳。
- 草稿可靠保存优先于减少写盘次数。候选结果可合并小批持久化，后台／取消立即保存快照；养成只跟随已经成功的业务事件记账，不给每次点击写库。
- 深浅主题均保证可读，不以强制黑色界面代替能耗优化。实际收益受屏幕、亮度、网络和设备影响。

## 养成保留陪伴感，减少管理负担

小邮个人页展示当前形象、简短使用回顾与装扮。轻量记录真实成功的协作事件，不为签到、计时、经验奖励增加周期任务；收到新邮件不能变成唤醒养成进程的理由。

首期不迁入桌面的前台心跳、日常点击计数、商店自动预览与循环装扮动画。成长与邮票如接入，使用本地事务和事件幂等记录，手账打开时再汇总。角色、装扮静态显示；大预览只在当前可见时按需播放一次。

不弹奖励遮正文，不显示催签到红点，不要求领积分才能用助手。养成可隐藏或暂停，不影响摘要和写作。手机与桌面进度不会因为同一个邮箱自动同步；跨端继承要另做明确的导入／同步协议，不能误导为已有功能。

## 能耗与可靠性验收

实现后同时比较“同版关闭小邮”和“开启小邮”两组，不拿不同手机的电池百分比做结论。相同设备、亮度、网络、缓存、通知和同步间隔，重复执行；记录耗时、CPU 时间、帧活动、网络字节和唤醒来源。支持设备再读功耗计；模拟器只验证停止逻辑，不能证明实际续航。

| 场景 | 必须验证 |
| --- | --- |
| 收件箱静置／长文阅读各 10 分钟 | 未唤起小邮时，无小邮循环动画、网络请求、周期计时或持续重组；结果缓存命中不产生模型请求 |
| 连续打开关闭小邮 20 次 | 请求不重复，取消释放资源，无动画／连接泄漏；回原邮件位置正确 |
| 生成中锁屏、退后台、切账号、旋转 | 后台无残留小邮请求；旋转不重复发起；候选恢复标记准确，不跨账号、不覆盖新草稿 |
| Wi-Fi／移动数据切换与弱网 | 有界超时和取消，无紧密重试、连接风暴；已收候选和原草稿可恢复 |
| 锁屏 8 小时对照 | 小邮额外定时唤醒、周期任务与主动网络为零；原邮件收信仍按用户设置执行，Doze 延迟单独记录 |
| 省电、发热、320 dp／200% 字号、深浅色 | 停止非必要动态；正文和按钮不遮挡；停止、重试和采用操作可达 |

上述时长为计划用例，尚未执行。验收报告应区分框架代管的邮件任务唤醒与小邮新增唤醒，不宣称整个邮件 App 零唤醒、零耗电或后台准点通知。发现明显额外 CPU／网络活动先定位，不只看掉电百分比。

## 实施顺序

1. 先做静态入口、半屏容器、原形象适配和生命周期停止骨架；使用合成数据验收交互与空闲耗能，不发布假 AI 按钮。
2. 接模型设置与三项前台任务、缓存、候选结果、取消／失败和草稿采用闭环；断网基础邮件功能完整可用。
3. 完成实际模型连接与内容隔离测试，再做真机能耗对照、锁屏和长后台测试。
4. 根据使用效果补自然语言检索、提醒等独立能力。养成与跨端同步分别设计，不绑在第一阶段发布。

## Android 官方依据

- [优化后台任务的电池使用](https://developer.android.com/develop/background-work/background-tasks/optimize-battery)：系统约束、任务调度和失败处理应避免无节制后台执行。
- [优化网络访问](https://developer.android.com/develop/connectivity/network-ops/network-access-optimization)：网络开销不只取决于数据量，合并请求和避免零碎反复连接有助于减少无线电活动。
- [Doze 与 App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby)：后台 CPU 和网络可能被推迟；不以新增小邮保活绕开系统策略。
- [Power Profiler](https://developer.android.com/studio/profile/power-profiler)：结合设备支持情况查看功耗数据和系统跟踪，不能用模拟器或单次电池百分比替代真机功耗结论。
