# macOS 统一凭据保险库

新版使用应用原生 Security.framework 读取主密钥，新建条目采用创建应用的默认访问控制，不再授权通用 `/usr/bin/security` 工具。启动时只允许当前邮箱主动解锁；后台和状态查询禁用授权界面，并在授权进行中立即返回等待状态。

2.8.4 及更早的统一保险库使用 `credential-vault-key:v1` 和第一版加密格式。新版在用户主动解锁旧保险库后，验证完整数据，再创建应用专属的 `credential-vault-key:v2`，使用不同随机主密钥和新的认证标记重新加密。原文件仅在新文件完整写入并 fsync 后原子替换；取消、主密钥缺失、数据损坏或写入失败时保留原文件，不自动覆盖密钥。旧主密钥及独立旧条目的访问控制不被程序直接改写或删除，避免破坏用户的其他数据副本；这些历史条目仍保留其原有权限，后续清理需要单独核对。

保险库继续存于用户应用目录的 `credentials.v1.enc`；文件名保留兼容，内容格式已升级。使用 AES-256-GCM、每次更新的新 nonce、当前用户专属文件权限。主密钥只保存在系统钥匙串，密码不进入命令行参数、日志、邮件备份或普通便携包。加固后的文件不能由 2.8.4 及更早版本解密，邮件数据库、原文、草稿和配置不改变。不要单独删除新主密钥。

同一请求中的取消不会反复弹窗；状态刷新保持静默，下一次用户点击解锁允许重试。启动恢复的重复调用不会再次提示已取消的邮箱。缓存状态锁只保护短时更新，后台查询不会等待另一个邮箱的系统授权。

当前发布尚未配置稳定的 Developer ID 签名，也未接入 Touch ID。严格的应用访问边界下，跨版本升级可能仍需为一个主密钥重新确认，所有已迁移邮箱共用它。免于每次升级重新授权需要稳定的应用签名；不以自动扩大系统工具权限替代这一条件。钥匙串锁定、系统策略或用户撤销授权也可能要求确认。

回归检查使用模拟系统凭据、临时加密文件验证安全迁移、旧密钥不能解密新文件、原子替换失败保留数据、取消重试、同请求抑制重弹及并发状态响应。真实临时钥匙串创建测试仅在隔离 CI 环境运行。
