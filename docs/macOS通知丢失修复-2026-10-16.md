# macOS 新邮件通知未显示

## 定位

安装版 `v2.8.22` 的邮箱后台同步正常。应用内通知策略为“全部”，macOS 的 MailAI 通知、桌面横幅、通知中心和声音也均已开启。

本机系统日志在 11:30 记录 `Legacy client … connecting to modern client. You can't mix modern clients with legacy clients.`，12:16 收到新邮件时记录 `Denying message 3 from connection <LegacyConnection …>`。应用的原生实现仍使用 `NSUserNotificationCenter`，而同一个应用标识已被系统按现代通知客户端登记，旧接口提交因此被系统拒绝。

原实现只确认 Cocoa 回调已排队，不能确认系统接受通知；邮件的 `notification_sent` 又在提交前写入，拒绝后没有重试，测试按钮也会误报“系统通知已开启”。

## 修复

- 邮件、待办与工作流提醒统一使用 `UserNotifications.UNUserNotificationCenter`，移除旧通知中心及其委托，避免同一应用混用接口。
- 保留前台横幅和声音，以及点击通知后打开原账号邮件或任务的行为。委托保持强引用，每条邮件通知使用账号与邮件 ID 生成稳定标识，任务使用独立标识。
- 每次提交检查系统授权并等待原生 completion handler；权限不足、系统拒绝或超时均返回失败。初次授权请求只由用户点击测试通知触发，后台收信不弹授权请求。
- 测试通知按钮依据真实授权及提交结果提示，不能把“已排队”当作“通知已开启”。系统接受提交仍不保证用户看到横幅，专注模式等系统策略可能影响展示。
- 新邮件通知采用数据库领取令牌和 60 秒租约，系统确认提交后才记为成功；失败和进程中断可在租约到期后重试，过期回调不能覆盖新的领取结果。
- 本地提醒调度独立重试待提交的邮件通知，每批最多 5 封，重新核对通知偏好；已经阅读的邮件不再补弹横幅。重试不依赖邮箱登录或新一轮收信。
- 未打包的 Python 进程禁止创建现代通知中心，防止 macOS 原生断言直接终止源码进程。源码运行保留现有应用内提示，不因原生通知重试而唤醒空队列。
- 增加固定版本的 `pyobjc-framework-UserNotifications` 构建依赖及打包导入。历史已确认记录保持原值，避免升级后批量弹出旧邮件通知。

## 验证

- `tests/test_macos_notifications.py`：系统拒绝、授权未定、明确授权、提交超时、测试按钮结果、多账号稳定标识、通知点击与关闭、前台展示、裸 Python 保护、数据库租约、崩溃恢复、失效回调、失败重试与已读抑制。
- 本机实际 PyObjC 桥接：创建现代通知内容、请求与委托，验证包含 block 回调的原生方法签名；不向真实邮箱发信，也不发送真实系统通知。
- 最小 PyInstaller 程序：验证冻结程序可导入 `UserNotifications`、创建请求与委托，无需接入真实账号。
- 既有邮件到达、待办通知、Dock 未读角标、节能调度、Windows 通知及国际化回归均通过；最终完整离线发布门禁 `243/243` 通过，前端产物新鲜度与 `git diff --check` 通过。

源码修复不会改变当前运行的安装包，需要发布并更新应用后生效。本项属于兼容性修复，随包含新增原生菜单能力的 `v2.9.0` 一起发布，不覆盖 `v2.8.22`。
